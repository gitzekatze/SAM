# SAM code review (audit)

**Date:** 2026-11-07
**Revision:** `3a4503c` (main)
**Scope:** the whole repository: 10 Rust crates (12.9k lines), the Qt/QML GUI (3.3k lines), packaging and docs.

**Method:**
- I read the security-critical paths: extraction, launcher generation, sandbox construction, launch, D-Bus/portal handling, repair logic and the GUI's text rendering.
- I verified every suspected issue I could test with a probe AppImage on the host (CachyOS, KDE Wayland, kernel 7.3, Landlock ABI 11).
- Findings are marked **verified** (reproduced) or **review** (from reading the code).

## Verdict

The core sandbox is well built:
- Bubblewrap layout with a private home and synthetic `passwd`.
- `--cap-drop ALL`, `--new-session`, `--clearenv` and a read-only root.
- Landlock with abstract-socket scoping, a baseline seccomp filter and a private `/dev/shm`.
- A method-level portal filter.
- Extraction is careful.

The weak points are elsewhere, in the layers built *around* the sandbox to make apps "just work". Several of them **trust text that the sandboxed app or the AppImage controls**:
- **The sandboxed app's stderr** decides when SAM downgrades the backend, and what it offers to grant.
- **The AppImage's metadata** is rendered as rich text and copied into the menu entry.

That breaks the threat model in `docs/security.md` ("individual AppImages may not be trusted"). Three findings are high severity. All three can be fixed without architectural changes.

## Findings

| # | Severity | Finding | Status |

| H3 | High | HTML injection from AppImage metadata into the GUI, triggering network requests when SAM starts | verified |

### H1: The sandboxed app can downgrade its own sandbox (verified)

`launch::run_auto` retries with the next backend when `classify_failure` reports a setup failure. That decision rests entirely on the stderr of the process tree:
- any line starting with `bwrap:` for Bubblewrap;
- `Traceback (most recent call last)` or `bubblejail:` for Bubblejail;
- `Error:` for Firejail.

The sandboxed app writes to that same stderr.

**Reproduced:** the probe printed `bwrap: Can't mount proc …` and exited with code 1. SAM switched it to Bubblejail and **stored that choice permanently** (`picked for this app: Bubblewrap could not set up the sandbox`). Bubblejail does not apply SAM's Landlock layer (no abstract-socket blocking), its portal method filter or its seccomp baseline. With `security.allow_firejail` on, the chain continues to Firejail (setuid).

**Fix:** decide "setup failed" from Bubblewrap itself, not from the output:
- `bwrap --json-status-fd` reports `child-pid` once the sandbox exists; no such event means a setup failure.
- Alternatively, the in-sandbox helper writes a marker before `exec`.

Only fall back when that signal is missing. Never fall back to a backend with fewer protections without asking the user.

### H2: App output can grant escape-capable D-Bus access with one click (verified)

`repair::analyze` turns `The name X was not provided` into `FixAction::Add { dbus.session.allow, X }` with risk **Medium**. `AppPage.applySuggestion` asks for confirmation only for High/Dangerous/compat, so this is applied with one click.

**Reproduced:** the output `…ServiceUnknown: The name org.freedesktop.systemd1 was not provided` produces "A desktop service is blocked → allow org.freedesktop.systemd1" (Medium).

On the session bus, `org.freedesktop.systemd1` is the user's systemd manager. `StartTransientUnit` runs any command as the user, **outside the sandbox**. The same applies to `org.kde.KWin` (scripting), `org.kde.plasmashell` (`evaluateScript`), `ca.desrt.dconf`, `org.freedesktop.Flatpak` and `org.freedesktop.portal.Flatpak`.

**Fix:**
- A deny list of names that must never be suggested, also enforced when added by hand unless explicitly confirmed.
- Suggestions derived from app output always need confirmation.
- Their wording should say plainly that the *app* is asking for this.

### H3: HTML injection from AppImage metadata into the GUI (verified)

No QML text element sets `textFormat`, so the default `AutoText` renders HTML. App names and comments come from the AppImage's desktop file, and the overview shows them **for every AppImage in the scan folders, without any user action**.

**Reproduced:** an AppImage named `<b>Totally Safe</b><img src="http://127.0.0.1:18799/tracking.png">` made the GUI fetch `/tracking.png` from the test server as soon as SAM opened, and rendered the bold text.

**Effects:**
- A downloaded file learns when, and from which IP, the user opens SAM.
- It can restyle its own card and dialogs (UI spoofing in a security tool).

**Fix:**
- `textFormat: Text.PlainText` on every element that shows app-provided text (names, comments, paths, log text, suggestion texts, dialog subtitles built from app names).
- Also strip control characters and limit lengths in `metadata_from_desktop`.

### M1: Untrusted `MimeType` in the launcher (review)

`desktop::launcher_contents` copies `MimeType=` from the AppImage unchanged. An app can declare `x-scheme-handler/https`, `application/pdf` or `inode/directory` and become a candidate handler (or the default, where none is set). Files opened through the launcher are then bound **read-write** into the sandbox (see L5).

**Fix:**
- Filter out scheme handlers and broad types.
- Show the declared types in the review step.
- Never make SAM launchers default handlers on their own.

### M2: The link opener sends sandbox paths to the host (verified)

The `xdg-open` shim turns local paths into `file://` URIs and calls `OpenURI` on the host portal. Paths inside the sandbox (private home, `/opt/app`, `/tmp`) mean something different on the host.

**Reproduced:** the app saved `~/sam-audit-export.txt` in its private home and called `xdg-open`. The shim reported success (exit code 0); no such file exists on the host. The host either opens nothing or **a different file with the same name**.

**Fix:** for local files, use `OpenURI.OpenFile` with a file descriptor (the portal's intended way). This needs fd passing, for example a small mode in `sam-jail-run`. Until then, refuse local paths and say so, rather than reporting success.

### M3: Landlock reported as requested, not enforced (review)

- `sam-jail-run --sandbox-exec` prints the Landlock status only with `SAM_DEBUG`.
- A failure only goes to the app's stderr ("landlock not applied"), and the launch continues.
- The launch log writes `landlock: true` before the app starts.
- Partial enforcement (older kernels) is never surfaced.

**Fix:** have the helper report its status on a dedicated fd (or the status fd from H1); log and show "fully / partially / not enforced".

### M4: "Grant folder" can target sensitive paths (verified)

`denied_home_path` takes any `/home/…` path from a "permission denied" line and suggests read-write access to its parent. The output `EACCES … '/home/user/.ssh/id_ed25519'` produces "grant read/write to /home/user/.ssh". This is High risk, so a confirmation dialog appears, but its text is app-driven.

**Fix:** apply `risk::is_sensitive_path` (it already exists) and never suggest credential locations.

### M5: Local network only exposes app ports on host loopback (review)

`pasta -t auto` forwards every port the app listens on to the host's loopback. A malicious app can bind a port that a host tool expects (a dev server, an admin UI) while the real service isn't running, and receive whatever the browser or tools send to it (cookies for `localhost`, for example).

**Fix:**
- An explicit list of app ports (with a sensible default per app, e.g. the web-UI port), as for `host_ports`.
- Or `auto` restricted to unprivileged high ports, with a visible list.

### M6: Portal identity imitates Flatpak's runtime files (review)

`portal_identity::Instance` creates `/run/user/<uid>/.flatpak/<random>/` with `create_dir_all` and deletes it with `remove_dir_all` on drop. If the random id collides with a real Flatpak instance, SAM overwrites its `info`/`bwrapinfo.json` and then **deletes the real instance directory**. The approach also depends on undocumented xdg-desktop-portal behavior (tested with 1.22.1), and `flatpak ps` will list SAM apps.

**Fix:**
- Use `create_dir` (fail if it exists) and retry with a new id.
- Never delete a directory SAM didn't create.
- Detect the portal version and fall back cleanly.
- Document it as a compatibility layer that can break.

### M7: Untrusted images parsed outside any sandbox (review)

`backhand` (in-process), `unsquashfs` and `bsdtar` all run on untrusted AppImages in SAM's own process context. `backhand` is memory-safe Rust and limits are enforced, but the C tools have a CVE history (unsquashfs symlink traversal before 4.5.1).

**Fix:** run extraction itself in a minimal Bubblewrap sandbox: read-only source, write-only target, no network. That's the same pattern as the `--appimage-extract` fallback.

### Low

- **L1** `notify-send` receives app names in title and body; notification servers render markup in the body.
- **L2** The runtime directory is per app, not per launch (`/run/user/<uid>/sam/<id>`). Two instances of one app overwrite each other's files. They keep working only because each sandbox holds the old inodes through its bind mounts (verified with two instances). Per-launch directories would remove the fragility.
- **L3** The Bubblejail backend always writes to the real `~/.local/share/bubblejail/instances`, ignoring `SAM_DATA_DIR`, so tests and isolated runs leave state in the real home.
- **L4** `run()` writes `profile.auto_backend` back at exit and can overwrite a change the user made while the app ran (for example "set to Automatic", which clears it).
- **L5** Files passed with "Open with" are always bound read-write, even if the app only views them.
- **L6** Seven `unwrap()` calls in `launch.rs` (mutex poisoning would panic the launcher), and 43 ignored results (`let _ =`) outside tests. Some matter: failures restoring hidden menu entries go only to stderr, and the GUI never sees them.
- **L7** The launcher comment says "sandboxed by **Sam**" (a rename artifact; the brand is "SAM").

## Architecture and code quality

**Strengths**
- **Clear layering:** core model → storage/detect/intake/profile → backends → runner → CLI. The GUI talks only to `sam-jail --json`, which keeps the trusted surface in Rust.
- **Careful filesystem handling:**
  - extraction refuses traversal and intermediate symlinks, and never writes through existing entries;
  - writes are atomic;
  - app ids and preset names are validated strictly.
- **Security layers are independent:** mounts, Landlock, seccomp, the D-Bus proxy and the portal filter. One mistake in one layer doesn't open everything.
- **Good tests for a young project:** 86 tests, including an end-to-end sandbox test, an overview/menu test and cross-backend parity tests.

**Weaknesses**
- **Text heuristics are security inputs.** `classify_failure`, `repair::analyze` and `needs_network_by_purpose` all pattern-match strings. That is fine for *suggestions*, but must never drive automatic changes (H1) or unconfirmed grants (H2).
- **Three hand-written backend translators.** The parity tests check only network, X11, GPU, sound, home and the portal. Device nodes, sockets and environment differences are not covered.
- **Large files with mixed responsibilities:** `sam-jail-cli/src/main.rs` (1,167 lines, one large `match`), `sam-runner/src/ops.rs` (959) and `gui/qml/AppPage.qml` (682).
- **Stringly typed fixes.** `FixAction::Set { key, value }` uses dotted strings checked only at runtime. A typo in a repair step fails when the user clicks it.
- **Flatpak imitation** (portal identity) is the most fragile part of the codebase; see M6.

## Tests

- **There are no adversarial tests:**
  - malicious stderr (H1, H2);
  - malicious metadata (H3, M1);
  - hostile SquashFS images (fuzzing `peek`, `metadata_from_desktop`, the built-in extractor).
- **No GUI tests** beyond manual screenshots. A QML test for plain-text rendering would have caught H3.
- **Not covered:** the end-to-end sandbox test skips itself without Bubblewrap; there is no CI, and nothing outside CachyOS has been tested.

## Documentation

`README.md` and `docs/security.md` describe the features accurately, with these exceptions:
- **"Links open in your normal browser"** is true for URLs, but opening local files is broken (M2).
- **`docs/security.md`** does not mention that repair suggestions and the automatic backend fallback react to app-controlled output (H1, H2), nor the Flatpak-imitation caveat beyond one line (M6).
- **`docs/whitepaper.md`** still describes features that don't exist (eBPF network filtering, domain-filtered network), and `SESSION.md` (internal handover notes) sits in the repository root.

## Recommended order

1. **H1, H2, H3 and M4** (small, contained changes):
   - Bubblewrap's status fd for setup failures;
   - a D-Bus deny list, with confirmation for anything derived from app output;
   - `PlainText` everywhere app text is shown;
   - the sensitive-path filter.
2. **M1, M2, M3** (launcher MIME filtering, fd-based file opening, real Landlock status).
3. **M5, M6, M7** (explicit app ports, safe instance directories, sandboxed extraction).
4. **Adversarial tests and fuzzing** for the above, then CI and multi-distro runs.
5. **Splitting `main.rs` and `ops.rs`**, and typed permission keys for repair steps.

## Resolution (same day)

All findings were addressed. The attacks are regression tests in
`crates/sam-runner/tests/adversarial.rs`.

| # | Fix |
|---|---|
| H1 | `setup_failed` comes only from bwrap's `--json-status-fd` (no `child-pid`). App-printed `bwrap:` lines are ignored. Automatic fallback goes to Bubblejail only, and Firejail never. Re-tested: the fake-error probe stays on Bubblewrap. |
| H2 | `permissions::dangerous_bus_name` (systemd1, Flatpak, impl.portal, KWin, plasmashell, klauncher, kded, krunner, ksmserver, kglobalaccel, GNOME Shell/SessionManager, dconf, wide wildcards). The analyzer refuses these (explanation only). A hand-added name is rated Dangerous, triggers a warning and needs GUI confirmation. `Suggestion.from_app_output` makes the GUI always confirm and say that the app asked. |
| H3 | `util::display_safe` cleans every desktop-file field at the source. QML uses `Util.plain`/`PlainText` for app text and paths (`Util.tildify`) and `Util.esc` in rich-text spots. Re-tested: HTML in the name and in the file name renders as text, with no network requests. |
| M1 | `desktop::launcher_mime_types` drops scheme handlers, `inode/*`, executables, desktop files, AppImages and generic types. MIME syntax is validated at intake. |
| M2 | The shim opens local files with `OpenURI.OpenFile` and a file descriptor (via python3-gobject); without it, it refuses with an error instead of reporting success. |
| M3 | The helper reports `landlock: …; seccomp: …` on a private fd that is closed before exec. It's logged as `# enforced:` and shown on the app page; "unknown" is shown if no report arrives. |
| M4 | Grant-folder suggestions skip sensitive paths, the home directory itself, and anything outside home. |
| M5 | `-t auto` excludes ports 1–1023 and well-known local service ports; `network.app_ports` restricts it to an explicit list. |
| M6 | Instance directories are created with `create_dir` (retried on collision); SAM only ever deletes directories it created. The limits are documented. |
| M7 | The built-in reader (`sam-jail dev extract-squashfs`), unsquashfs and bsdtar run inside a minimal Bubblewrap sandbox; the log states whether extraction was isolated. |
| L1 | Notification text goes through `display_safe` and `&` is escaped. |
| L2 | One runtime directory per launch (`<runtime>/<id>/launch-<pid>-<time>`), removed afterwards. |
| L3 | With `SAM_DATA_DIR` set, Bubblejail state goes there (`XDG_DATA_HOME` for bubblejail). |
| L4 | `run()` no longer writes `auto_backend`; only `run_auto` saves it. |
| L5 | `filesystem.opened_files` (`ro`/`rw`); media players default to `ro`. |
| L6 | No `unwrap()` left in launch code; menu-restore problems are returned by `remove` and shown. |
| L7 | "sandboxed by SAM". |
| Docs | `security.md` has a "What SAM never trusts" section, plus notes on the Flatpak imitation and isolated extraction. The whitepaper has a status note. `SESSION.md` moved to `docs/session-notes.md`. |
